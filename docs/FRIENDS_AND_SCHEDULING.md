# Друзья и совместное планирование

Страница `/friends` использует существующие аккаунты и профиль. Код `ABCD-EFGH` генерируется PostgreSQL при создании аккаунта; миграция выдаёт коды существующим пользователям. Уникальность защищена ограничением БД. Публичного поиска аккаунтов нет. Отправка по коду ограничена 20 попытками в час на пользователя, включая неверные коды; доступность — 120 проверками в час. Лимиты сохраняются в БД.

Дружба хранится одной упорядоченной парой пользователей. Теги и видимость email принадлежат пользователю. По умолчанию email скрыт. Удаление друга не удаляет встречи и ответы, но новые приглашения требуют действующей дружбы непосредственно в транзакции отправки.

## Встреча и ответы

Единственная запись `events` принадлежит организатору. `collaborative_meetings` содержит версию и признак отмены; `meeting_participants` — приглашения и текущие ответы. Отдельных локальных копий события нет. Принятые приглашения включаются в стандартные чтения календаря; ожидающие и отклонённые не блокируют время. Приглашённый меняет только свой ответ. Прямые изменения через обычные event API и импорт Google также проверяют владельца.

Перенос увеличивает версию, сохраняет старые ответы в `invitation_responses`, переводит все действующие приглашения в `pending` и уведомляет участников. Устаревший ответ возвращает 409. Перед применением нового времени проверяется доступность. Отказанное предложение оставляет исходное время. Отмена приглашения сохраняет ограниченный снимок истории: отозванный участник не получает будущие изменения встречи. Отменённую общую встречу нельзя восстановить вместе с прежними согласиями; для новых приглашений создаётся новая встреча.

Изменения чата, состояние диалога, идемпотентный результат, записи приглашений и persistent notifications сохраняются в общей транзакции. HTTP использует `request_id` UUID и отпечаток тела, чат — существующие `(user, session_id, request_id)`. Доменный advisory lock берётся до пользовательского lock; HTTP к внешним провайдерам всегда выполняется вне транзакции. Эта первая реализация сериализует короткие доменные записи между аккаунтами, чтобы исключить гонки согласования. Долгие внешние запросы этот lock не удерживают.

## Доступность и приватность

Локальная занятость учитывает встречи, принятые приглашения и синхронизированные события Google, включая события на весь день и длительные интервалы. Внешняя проверка читает все доступные Google-календари и CalDAV-календари Яндекса. Запрашиваются время, прозрачность и технические идентификаторы; названия, описания и участники не нужны. Повторения разворачиваются провайдером. Кэш содержит только интервалы; техническая связь с event_id позволяет исключить саму переносимую встречу. Пересечения объединяются, одинаковое событие из нескольких источников не удваивает занятость.

Организатор получает только `free`, `busy`, `unknown`, `complete` и общие интервалы. Ошибка провайдера не считается свободным временем. Предложенные интервалы при неполной проверке обозначены как предварительные. Подбор учитывает длительность, IANA-зоны и доступные часы каждого участника, шаг 15 минут, горизонт 14 дней, максимум шесть предложений. Выбор интервала сам по себе не создаёт встречу.

Google и Яндекс используют существующие очереди синхронизации и OAuth-хранилища. Принятие/отклонение и изменения общей встречи ставят в очередь тот же event_id для календарей участников. Zoom создаётся и изменяется интеграцией организатора; приглашённым передаётся общая ссылка присоединения. Импорт из календаря участника не меняет событие организатора.

Используется существующая доставка сохранённых сообщений Гены: интерфейс опрашивает новые данные каждые пять секунд, повторяет запрос при восстановлении сети и показывает счётчики. Это polling, без отдельного WebSocket/SSE-канала. Сообщения остаются после перезагрузки и имеют явное состояние прочтения.

## API и simple_llm

- `GET /api/social/people`: профиль, друзья, входящие/отправленные заявки.
- `GET /api/social/meetings`: доступные совместные встречи и предложения.
- `POST /api/social/operations`: транзакционные изменения с request_id.
- `POST /api/social/availability`: приватная проверка и варианты времени.

Контракты документированы в OpenAPI. Все маршруты используют существующие auth и CSRF.

`simple_llm` дополнен операциями `friend_request`, `friend_requests`, `friend_availability`, `invite_friends`, `respond_invitation`, `propose_reschedule`, `resolve_reschedule`; `create_meeting` принимает имена друзей или персональный тег. Модель не получает DB IDs. Go разрешает имена в подтверждённых друзьях, проверяет права и уточняет неоднозначность. Незавершённая совместная команда сохраняется в компактном `social_pending`. Legacy SemanticPlan/NLP не расширялись.

## Проверки

```powershell
$env:TEST_DATABASE_URL='postgres://test-user@127.0.0.1:5544/semantic_test?sslmode=disable'
go test ./...
go vet ./...
pnpm --dir web test
pnpm --dir web build
pnpm --dir web exec playwright test e2e/friends.spec.ts
python scripts/social_smoke.py --base-url http://127.0.0.1:8083
```

Последняя команда создаёт два новых тестовых аккаунта и обращается к действующему `simple_llm` через HTTP: код, заявка, доступность, приглашение, перенос, принятие, приглашение по тегу, отказ, отмена. Пароли, cookies и токены не выводятся. Браузерный тест также использует настоящие HTTP/API и аккаунты, проверяет обновление без перезагрузки, копирование, мобильную вёрстку и отсутствие дублей. Protocol integration tests проверяют Google/Яндекс/Zoom с тестовыми HTTP-провайдерами; для проверки настоящего внешнего аккаунта нужен отдельно подключённый тестовый календарь.

Источники протокола: [Google Events list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), [CalDAV RFC 4791](https://www.rfc-editor.org/rfc/rfc4791.html).

## Развёртывание и откат

Миграция `007_friends_scheduling.sql` аддитивная, без удаления production-данных. Старая версия продолжает работать с расширенной схемой. Перед переключением релиза требуется проверенный PostgreSQL dump, сохранённые конфигурация и предыдущий образ. Откат приложения возвращает предыдущий образ и конфигурацию, не удаляя новые таблицы и историю. Автоматический destructive down migration не предусмотрен.
