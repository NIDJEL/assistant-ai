# Multi-Action в simple_llm

Дополнение от 26 октября: реализованы `atomic_group`, серверные токены выбора/отмены шага и отображение внешних статусов. Актуальные границы и проверки — в [TOP-10](TOP10_IMPLEMENTATION.md). Обычные независимые команды по-прежнему могут завершаться отдельно.

## Результат и границы

Один запрос может содержать от двух до пяти действий. Старый одиночный `intent + arguments` продолжает работать. Новый путь использует тот же `assistant.Service`, проверки прав, календарную логику, подтверждения и repository. Legacy planner не переключается на новый протокол автоматически.

Для запроса «Создай встречу с Колей в 8, добавь задачу купить продукты и напомни позвонить маме в 10» задача может сохраниться сразу; встреча и напоминание остаются в плане до уточнений. «В 8» не превращается молча в 20:00. Неизвестный человек допускается в личной встрече; приглашения требуют отдельной явной просьбы и разрешения существующего social executor.

Multi-Action не означает транзакцию через несколько реплик пользователя. В каждой реплике эффекты, состояние плана и кэш `request_id` сохраняются одной транзакцией. Уже подтверждённые предыдущими ответами действия остаются выполненными. При ошибке хранилища текущая транзакция полностью откатывается. Ошибка аргументов или незаполненный шаг сохраняются отдельно и не мешают независимым шагам.

## Контракт

```json
{
  "intent": "multi_action",
  "arguments": {
    "steps": [
      {
        "key": "a",
        "source": "Создай задачу Отчёт",
        "operation": {
          "intent": "create_task",
          "arguments": {"title": "Отчёт"},
          "confidence": "high",
          "clarification": null
        }
      },
      {
        "key": "b",
        "source": "затем заверши её",
        "depends_on": ["a"],
        "operation": {
          "intent": "complete",
          "arguments": {"target": {"type": "step", "value": "a"}},
          "confidence": "high",
          "clarification": null
        }
      }
    ]
  },
  "confidence": "high",
  "clarification": null
}
```

`key` — уникальный локальный ключ `[a-z][a-z0-9_]{0,31}`, не DB ID. `source` — точная подстрока текущего сообщения. Этот фрагмент передаётся существующим защитным проверкам времени и приглашений вместо всего сообщения. Все источники проверяются до исполнения. Граф допускает только ссылки на более ранние шаги; циклы, неизвестные зависимости и повторяющиеся ключи отклоняются.

Вложенные планы и управляющие `confirm`, `cancel`, `continue`, `select`, `choose_time`, `chat` внутри начального плана не выполняются. Подтверждение нельзя спрятать вторым шагом рядом с удалением. Неизвестные поля аргументов и DB IDs остаются запрещены строгим декодером. Невалидный отдельный шаг становится `failed`; другие независимые шаги могут выполниться. Невалидная структура самого плана не выполняется целиком.

Для исправления или ответа другому шагу:

```json
{
  "intent": "resume_action",
  "arguments": {
    "key": "a",
    "operation": {
      "intent": "continue",
      "arguments": {"changes": {"time": "20:00"}},
      "confidence": "high",
      "clarification": null
    }
  },
  "confidence": "high",
  "clarification": null
}
```

Для `failed` передаётся полная исправленная операция. Вложенный `cancel` отменяет выбранный шаг и его ещё не выполненных потомков; обычный `cancel` отменяет весь остаток плана. `done` повторно не запускается. Нельзя заменить незавершённый план новым `multi_action`: сначала нужно закончить или отменить сохранённый план.

## Состояние, ссылки и подтверждения

`domain.State.Actions` содержит `ActionPlan`: исходное время, исходный контекст ссылок, активный ключ, операции и их зависимости, результаты и отдельный `Pending` каждого шага. Состояния: `ready`, `waiting`, `done`, `failed`, `blocked`, `cancelled`. Поле `State.Pending` отражает текущий ожидающий шаг для совместимости существующих кнопок и одиночного диалога.

Модель получает ограниченный `context.actions` и `active_action`, без DB IDs. Там есть источники, статусы и валидные незавершённые операции. Обычный `continue` относится к активному шагу. Одновременный ответ сразу нескольким ожидающим шагам в текущем контракте просит отвечать по одному. Срок действия плана — 30 минут от исходного запроса; продление отдельного pending не продлевает весь план.

Независимые ссылки `last` используют контекст исходного запроса. Создание соседней задачи не перенаправляет их на новую запись. Зависимый `target.type=step` разрешается только в один результат объявленной завершённой зависимости. Угадывать DB ID или брать последний результат другой ветви нельзя. Для зависимости от поиска доступен порядковый выбор из его результата.

У каждого удаления, batch или конфликта свой существующий preview и snapshot. Одно «да» завершает только текущий шаг. При невалидном новом ответе модели опасные preview снимаются; сами незавершённые шаги сохраняются для исправления и нового preview. Ошибки формата не разрешают повторно подтвердить старое удаление.

Операции и даты сохраняются до следующих уточнений. Относительные выражения замораживаются относительно исходной реплики; `absolute_time` сохраняет точный момент задержки, включая секунды. Исполнитель всё равно проверяет актуальность времени и существующих записей на момент выполнения.

`time_ambiguous:true` есть у создания и `changes`. LLM передаёт этот признак для неразрешённой части суток. Консервативная Go-проверка дополнительно перехватывает простые формы «в 8»/«в восемь» даже при ошибочном `time:"20:00"`. Это не полный языковой парсер: более сложные выражения по-прежнему требуют корректной интерпретации моделью. Явные `08:00`, `20:00`, «утра», «вечера» и относительные таймеры сохраняют свою семантику. Проверки неоднозначных участников имеют приоритет перед вопросом о времени совместной встречи.

## Ответ и внешние эффекты

`Response.operations` содержит по каждому шагу `key/status/reply` и, для выполненного шага, действие и IDs результата. `applied` отмечает выполнение именно в текущей реплике: ранее выполненный шаг не считается новой мутацией при позднем поиске его результата. Это API-результат, не вход LLM. Основной ответ перечисляет статусы всех шагов; карточки, кандидаты и подсказки относятся к активному уточнению. Старый UI показывает общий текст и стандартные карточки без обязательной миграции.

Google/Zoom синхронизируются после локального commit для реально изменённых результатов текущей реплики, даже если другой шаг ещё ожидает уточнения. Ошибка внешнего сервиса не выдаётся за успешную синхронизацию. Атомарной транзакции одновременно с внешними календарями нет. Подготовка доступности остаётся вне write-транзакции. Существующие фоновые механизмы уведомлений и Яндекс Календаря не заменены.

## Проверки и воспроизведение

```powershell
go test -count=1 ./...
go vet ./...
go test -count=1 ./internal/assistant -run 'Multi|AmbiguousClock'
go test -count=1 ./tests/contract -run 'MultiActionPostgres'
```

Для PostgreSQL требуется отдельная loopback база `*_test` в `TEST_DATABASE_URL`; тестовый fixture очищает её. Для полного существующего набора используйте имя, содержащее `semantic_test`, как в CI. Live-тесты дополнительно требуют `GENA_TEST_MULTI_LIVE=1`, корректного `APP_ROOT` и существующей конфигурации GigaChat. Они работают только с тестовыми аккаунтами в этой базе.

Проверяются: исходные три команды и цепочка уточнений, перезапуск Service с сохранённым состоянием, невалидный шаг рядом с валидным, запрет model IDs, зависимость от созданной записи, сохранение исходных ссылок, отдельные подтверждения, повтор одного request_id шестью concurrent callers, rollback при сбое сохранения и точность секунд таймера. Production-контракты проверяют изоляцию пользователей и durable pending. Результаты конкретного прогона находятся в `artifacts/multi_action_*.txt` и `artifacts/multi_action_go_test.jsonl`.

## Выпуск

Схема таблиц не меняется: план сохраняется в существующем JSON состояния. Включение — тот же `GENA_NLU_MODE=simple_llm`; отдельного экспериментального режима нет. После проверки нужно обычным способом собрать и выпустить приложение. Этот рабочий каталог сам по себе не обновляет работающий сервер. Откат на старую версию следует делать после завершения/отмены активных планов: старый runtime не знает о `State.Actions`.
