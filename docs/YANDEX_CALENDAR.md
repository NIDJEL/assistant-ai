# Яндекс Календарь

Интеграция отправляет задачи, встречи и напоминания из приложения в отдельный календарь «Ассистент Гена» через CalDAV. Создание, перенос, редактирование, завершение, удаление и восстановление синхронизируются автоматически. При первом подключении отправляются уже существующие дела с датой. Запись без времени становится событием на весь день; запись без даты не отправляется. Завершённые дела остаются в календаре с отметкой ✓ и не занимают время.

## Настройка

1. В существующем приложении [Яндекс OAuth](https://oauth.yandex.ru/) включите право **«Чтение и изменение содержимого календарей и списков дел» (`calendar:all`)** вместе с используемыми правами `login:info`, `login:email`, `login:avatar`.
2. Используйте прежние `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI`. Новый callback не требуется. `PUBLIC_URL` должен совпадать с адресом приложения.
3. Пересоберите приложение: `docker compose up --build -d app`. Миграция PostgreSQL выполняется автоматически при старте.
4. Откройте **Интеграции → Яндекс Календарь → Настроить → Подключить Яндекс Календарь** и разрешите доступ на странице Яндекса.

Обычный вход через Яндекс запрашивает только профиль. Подключение календаря запрашивает дополнительное разрешение и привязывается к текущему аккаунту приложения. Уже выданный токен входа нельзя превратить в токен календаря: пользователь должен один раз подтвердить расширенный доступ. [Документация OAuth о правах и повторном согласии](https://yandex.ru/dev/id/doc/ru/codes/code-url).

После подключения появляется статус, время последней синхронизации, число ожидающих записей и кнопки ручной синхронизации и отключения. На узких экранах панель доступна по кнопке «Интеграция» сверху. Другие сервисы пока показывают «Скоро».

## Синхронизация и хранение

- Фоновый процесс проверяет очередь каждые 15 секунд и при подключении; за проход обрабатывается до 50 записей. Большой первый импорт может занять несколько проходов.
- Изменения записываются в очередь в одной транзакции с событием. Это охватывает ручной ввод, чат, CSV, завершение и восстановление. Версия очереди предотвращает потерю изменений во время отправки.
- Постоянные UID и адрес ресурса обновляют существующее событие при повторной отправке. Запросы к Яндексу выполняются вне транзакции изменения дела.
- Токены шифруются AES-GCM с ключом, производным от `SESSION_SECRET`, и привязкой к пользователю. Они не возвращаются в API, браузер или журналы. Сохраните `SESSION_SECRET` при перезапусках: после его замены календарь нужно подключить снова.
- Токен обновляется через `refresh_token`; отозванный доступ требует повторного подключения. При временной ошибке очередь сохраняется и отправка повторяется.
- Отключение удаляет сохранённые токены и останавливает отправку. Уже созданные события остаются в Яндексе. Повторное подключение использует тот же календарь и UID.
- Данные направляются только из приложения в Яндекс. Изменения в Яндексе не импортируются; последующее редактирование дела в приложении обновляет его копию. Участники сохраняются в описании, без отправки приглашений.

Протокол: обнаружение `current-user-principal` и `calendar-home-set`, создание отдельного календаря `MKCALENDAR`, события `VEVENT` в формате iCalendar, `PUT`/`DELETE`. CalDAV использует логин Яндекса и OAuth-токен в Basic Auth; такой способ описан в [примере Яндекса](https://www.yandex.ru/support/yandex-360/business/admin/ru/security-service-applications). Адрес сервера — `https://caldav.yandex.ru/`. Адреса из ответов ограничены этим origin, перенаправления запрещены.

Яндекс может создавать календарь под адресом `events-N`, отличающимся от запрошенного. Приложение получает фактический адрес через `Location` либо повторное обнаружение календарей. При ошибке ранее сохранённый адрес восстанавливается по существующему календарю приложения, без повторного подключения. Имя `.ics`-ресурса совпадает с UID события: Яндекс хранит запись под этим именем, поэтому оно используется и при обновлении, и при удалении.

Название OAuth-приложения — **Ассистент Гена**. Новые коллекции получают это имя. Уже записанная системная коллекция со старым именем переименовывается через PROPPATCH при синхронизации; пользовательские названия событий и переименованные пользователем коллекции сохраняются. Старые URI/UID сохраняются для совместимости. Повторение хранится локально; CalDAV получает текущий occurrence без RRULE, поэтому при закрытом приложении серия сама не продвигается.

## Проверки

### Уведомления перед событием

Интервал `reminder_minutes` передаётся в `VALARM` вместе с исходным `DTSTART`: событие на 12:50 и уведомление за 50 минут экспортируются с `TRIGGER:-PT50M`. При нулевом интервале используется `TRIGGER:PT0S`. Отключённые сигналы и завершённые события экспортируются без `VALARM`. Редактирование интервала попадает в ту же устойчивую очередь синхронизации, что и переносы.

Используется стандартный сигнал `ACTION:DISPLAY` через CalDAV. Он не выдаёт разрешений Яндекс Браузеру и не включает сам по себе push, почту или приложение Яндекса. Канал доставки нужно разрешить в настройках календаря или события в Яндексе: [инструкция Яндекса](https://yandex.ru/support/yandex-360/customers/calendar/web/ru/plan-events/notifications). CalDAV-сигнал предназначен в том числе для синхронизированных календарных клиентов; доставка конкретного канала Яндекса требует проверки в подключённом аккаунте.

Тесты проверяют время начала, упреждение, отключение и сохранение/отправку настройки через PostgreSQL и HTTP-модель CalDAV. Это не подтверждение получения push на пользовательском телефоне.

```powershell
$env:TEST_DATABASE_URL = 'postgres://rhythm@127.0.0.1:5433/rhythm?sslmode=disable'
go test ./...
go vet ./...
pnpm --dir web test
pnpm --dir web build
pnpm --dir web exec playwright test integrations.spec.ts
```

Контрактный тест использует PostgreSQL и HTTP-модель Яндекса: OAuth/PKCE, шифрование, разные пользователи, переносы без дублей, временный сбой, параллельное изменение, обновление токена, удаление, восстановление, дела из чата и отключение. Живое подключение к пользовательскому Яндексу требует подтверждения доступа пользователем; HTTP-модель не подтверждает работу реального аккаунта.
